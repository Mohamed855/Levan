- حفظ خطة واحدة داخل docs/superpowers/plans ونسخة تسليم متطابقة في outputs. لا كود تطبيق تغير أثناء كتابة الخطة.

- لا seed أو migration أو كتابة في قاعدة بيانات فعلية خلال هذه الدفعة.
- لا commits/push ولا تعديل vendor.
- Task 1 لا يدعي حماية أوامر Artisan الخارجية أو overrides لاحقة داخل test؛ هذه تستكمل في اختبارات تكامل Task 4.
- Ruling: معالجة عطل الفواتير المحدد وحسابات seed الافتراضية مبكرًا لأنها عيوب مثبتة داخل نطاق الإقفال، دون تغيير جدول انتقالات الأعمال الحالي أو تشغيل DB. لا تعتبر هذه الوحدات مغلقة ولا يغني الإصلاح المحدود عن Tasks 5/9/10.
- Ruling: لا يعاد Builder من داخل `Tenancy::central`؛ يُنشأ Model على connection المركزي الصريح كي يبقى صحيحًا عند تنفيذ Yajra للاستعلام لاحقًا. التكلفة إن كان الافتراض خاطئًا: يلزم تكييف gateway مع اتصال مركزي مخصص، لا إعادة استخدام اتصال tenant.
- Ruling: إيصالات التحويل تحفظ على disk `local` الخاص بدل `public`، وتحذف إذا فشل تسجيلها المركزي. لا تزال آلية العرض المصرح به للإدارة وتوافق مرفقات workflow القديم ضمن Task 5/7.
- Ruling: إلى أن تستعاد بنية invoice/payment attempt وprovider callback وprovisioning كاملة، لا يمسح Checkout الجلسة ولا يعلن نجاحًا بعد OTP؛ يعيد خطأً واضحًا. التكلفة: الدفع العام غير متاح مؤقتًا بدل الإيهام بإنشاء حساب غير موجود.
- Ruling: محاولات الدفع تستخدم `checkout_token` UUID فريدًا وreceipt خاصًا؛ إعادة POST بنفس token تعيد المحاولة نفسها ولا تنشئ فاتورة ثانية. الكوبونات والـprovisioning لا تزالان غير موصولتين، لذلك لا تعد هذه المرحلة إقفالًا للـcheckout.
- Ruling: اعتماد/رفض تحويل بنكي ليس انتقالًا عامًا للحالة: يُقفل Bill وPaymentAttempt ثم يطلق Provisioning فقط لمحاولة site_checkout المدفوعة. في الرفض، الفاتورة بلا tenant تُلغى وفاتورة tenant قائم تعود unpaid، كما في السلوك القديم.
- Ruling: ترخيص المستخدمين ومفاتيح API وعمليات الاشتراك عبر tenant لا تكتب في قاعدة tenant. تُنفّذ عبر gateways على اتصال central صريح مع hashing للمفتاح، وقفل للفوترة/المقاعد، ويدور المفتاح دون حفظ قيمته الصريحة.
- Ruling: لم يُنقل legacy Namecheap/WHM كما هو لاحتوائه أسراراً وبيانات Whois ثابتة. المتاح الآن هو availability/DNS verification بإعدادات البيئة؛ الشراء أو النقل أو التجديد لا ينفذ حتى يختار مالك النظام registrar، التسعير، وهوية التسجيل.
- Security correction (pending test execution): سبب تسريب hashes في صفحة فاتورة الإدارة كان نسخ session checkout بالكامل إلى `bills.metadata`. صار إنشاء الفاتورة يمرر allowlist فقط، ويحفظ بيانات provisioning الحساسة في عقد داخلي لا تعرضه الـview؛ أزيل أيضاً OTP/expiry من التخزين الدائم.
- Financial correction (pending test execution): endpoint تغيير حالة الفاتورة العام لم يعد يستطيع جعل أي فاتورة checkout مدفوعة؛ تُزال `paid` من انتقالاتها وتوجد حماية ثانية داخل الـAction. تأكيد الدفع يظل حصريًا في callback المتحقق أو اعتماد التحويل البنكي، كي لا يُتخطى provisioning أو تسوية الكوبون.
- Security correction (pending test execution): إيصالات التحويل المخزنة على `local` لم تعد تُبنى كرابط `storage` عام؛ تنزيلها صار عبر مسار tenant محمي، يعيد فحص bill ownership وprefix المسار قبل قراءة الملف.
- Ticket correction (pending test execution): كانت صفحة Ticket في الإدارة تعكس صلاحية إظهار نموذج الرد ومغيّر الحالة مقارنة بالـroutes/Policies؛ صحح العرض ليطابق `tickets.reply` للرد و`tickets.update` للحالة.
