# LOT — الاختبار والإصلاح والمراجعة المشتركة

تاريخ إعداد الاتفاق: 2026-11-03 بتوقيت Africa/Cairo.

هذا الملف مرجع العمل المشترك بين المستخدم وCodex وGemini. لا توجد إدارة معتمدة للإنتاج بمجرد إنشاء هذا الملف.

## الأدوار ودورة العمل

1. المستخدم يحدد الإدارة أو الجزء المطلوب، وحدوده: Central / SuperAdmin أو Tenant أو الموقع العام.
2. Codex يقرأ الملفات المرتبطة مباشرة بهذا الجزء، وتعليمات المشروع، وبلاغات الـtester المتعلقة به، ويعد حالات اختبار قابلة للتنفيذ.
3. Codex ينشئ ملف الإدارة داخل `docs/qa/` باسم إنجليزي يوضح النطاق، مثل `tenant-dashboard.md`. هذا مثال تسمية فقط؛ لم يتم اختيار لوحة التحكم كبداية.
4. المستخدم يرسل Gemini لقراءة ملف الإدارة. Gemini ينفذ الحالات، ويسجل النتائج الفعلية، ويحقق في أسباب الإخفاقات ويصلحها ضمن النطاق المحدد، ثم يعيد الاختبار ويسجل الأدلة.
5. عندما يبلغ المستخدم بانتهاء الإصلاح، يراجع Codex التغييرات الفعلية ويعيد الاختبارات بصورة مستقلة، بما فيها السلوك الأصلي للبلاغ والتأثيرات على الوظائف المرتبطة.
6. أي إخفاق يعود إلى Gemini مع خطوات إعادة الإنتاج ومعيار القبول غير المتحقق. Codex يعتمد الإدارة فقط بعد اجتياز بوابة الإغلاق أدناه.

Gemini مسؤول التنفيذ والإصلاح. Codex مسؤول إعداد الحالات والمراجعة والقبول. يظل التسليم يدويًا عبر المستخدم وفق الاتفاق، ولا تُرسل مهام تلقائيًا إلى Gemini لمجرد إنشاء الملفات.

- الشيت مصدر للبلاغات، وملفات `docs/qa/` سجل التنفيذ والمراجعة. لا تعدل حالات الشيت ضمنيًا من خلال تحديث الملفات المحلية.

## حالات المتابعة

| القيمة | المعنى | المسؤول عن تسجيلها |
| --- | --- | --- |
| `not_run` | لم ينفذ الاختبار | Codex عند الإعداد |
| `in_progress` | التنفيذ أو التحقيق جارٍ | Gemini |
| `failed` | السلوك الفعلي يخالف المتوقع | Gemini أو Codex |
| `fixed_pending_review` | أُصلح الخلل وأعيد الاختبار، بانتظار Codex | Gemini |
| `passed_pending_review` | نجح الاختبار دون تعديل، بانتظار Codex | Gemini |
| `blocked` | التنفيذ متعذر بسبب مانع محدد موثق | Gemini أو Codex |
| `verified` | اجتاز المراجعة وإعادة الاختبار المستقل | Codex فقط |
| `reopened` | رفضت المراجعة النتيجة أو ظهر ارتداد | Codex |
| `not_applicable` | الحالة غير منطبقة، مع سبب يراجعه Codex | Codex |

حالة الإدارة: `awaiting_scope` ثم `prepared` ثم `in_progress` ثم `awaiting_review`، وتنتهي بـ`production_ready` بعد قبول Codex فقط. وجود مانع أو إخفاق يبقيها مفتوحة.

## محتوى ملف كل إدارة

### تعريف الدفعة

- معرف الدفعة، الإدارة، والحدود الوظيفية المشمولة.
- حالة الإدارة ووقت آخر تحديث واسم صاحبه.
- الفرع ومرجع الكود والبيئة المختبرة وإصدارات الأدوات المؤثرة.
- التغييرات الموجودة قبل البداية، والملفات المسموح تعديلها؛ تُحفظ أعمال المستخدم كما هي.
- بيانات اختبار وأدوار مطلوبة دون كلمات مرور أو أسرار أو بيانات شخصية حقيقية.
- خريطة الملفات: Routes / middleware / guard، Controller، FormRequest، Policy، Action أو Service، Model / Enum / Event / Job، DataTable أو Blade، JavaScript المشترك، والاختبارات. يُذكر غير المنطبق وسببه.
- مراجع `AGENTS.md` و`docs/architecture/golden-pattern.md` و`docs/baselines/golden-pattern-manifest.md` والأجزاء المنطبقة من نمطي assignments وproperties.
- قائمة بلاغات الـtester المنطبقة، مع نطاق القراءة وتاريخها، وأسئلة السلوك غير المحسومة.

### سجل الحالات

| معرف محلي فريد | المصدر / صف الشيت | السيناريو | الأولوية | حالة التنفيذ | دليل Gemini | نتيجة Codex |
| --- | --- | --- | --- | --- | --- | --- |

الجدول فارغ عمدًا حتى يحدد المستخدم أول إدارة. لكل حالة فعلية قسم تفصيلي يتضمن:

- الشروط المسبقة، الدور، المستأجر، والبيانات المستخدمة.
- خطوات مرقمة قابلة للتكرار، مع المدخلات المحددة.
- النتيجة المتوقعة القابلة للملاحظة ومعيار القبول.
- النتيجة الفعلية، ورسالة الخطأ عند وجودها، والأولوية وأثر العطل.
- سبب الخلل عند ثبوته، والملفات المعدلة، وملخص الإصلاح.
- أدلة التنفيذ: الأمر كاملًا، نتيجته ورمز خروجه، وقت التنفيذ ومرجع الكود؛ وللواجهة خطوات المشاهدة ولقطات مناسبة خالية من البيانات الحساسة.
- مراجعة Codex المستقلة، ونتيجة إعادة الاختبار، وسبب إعادة الفتح إن حدثت.

أي مشكلة جديدة تظهر أثناء التنفيذ تُضاف بمعرف محلي جديد، مع ربطها بالحالة التي كشفتها. لا تحذف الحالات الفاشلة أو الأدلة القديمة؛ تُضاف نتيجة المحاولة الجديدة.

## التغطية المطلوبة حسب ما ينطبق على الإدارة

- المسارات الأساسية، البيانات الفارغة، الحدود والقيم غير الصحيحة، التكرار، العلاقات، المعاملات والفشل الجزئي وتكرار إرسال الطلب.
- تسجيل الدخول والصلاحيات والأدوار، منع الوصول المباشر غير المصرح، وعزل بيانات وملفات المستأجرين وCentral / Tenant.
- إنشاء وتعديل وعرض وحذف وأرشفة واستعادة وحذف جماعي، مع الاستجابات والتنبيهات الصحيحة حيث تدعمها الإدارة.
- مصدر التحقق في FormRequest، التحقق المشترك في الواجهة، رسائل الأخطاء والحقول غير القابلة للتعديل.
- المسودات: حفظ بيانات ناقصة وملفات، استعادة المسودة، عزلها وتنظيفها بعد الإنشاء الناجح، وعدم ظهور زرها في التعديل.
- الجداول: الإحصاءات والفلاتر والبحث والترتيب والترقيم والتحديد والتصدير والحالة وروابط الإجراءات وصلاحياتها.
- المرفقات: قبول الأنواع والأحجام المسموحة، منع الوصول غير المصرح، المعاينة والتنزيل ومكونات العرض المشتركة.
- الواجهة: العربية وRTL، أحجام الشاشة، لوحة المفاتيح، المعالجات المشتركة، أخطاء Console وطلبات الشبكة الفاشلة، واتساق نماذج create / edit والعرض والمراجعة.
- توافق Golden Pattern وتعليمات المشروع؛ تُحول المتطلبات المنطبقة إلى حالات بمعايير قبول محددة.
- اختبارات ارتداد للخلل الأصلي والوظائف التي قد تتأثر بتغيير مكون مشترك، مع تسجيل أثر التغيير خارج الإدارة.

هذه محاور لإعداد الحالات من الكود الفعلي، وليست دليلًا على تنفيذها.

## تعليمات التنفيذ والتسليم إلى Gemini

اقرأ هذا الملف وملف الإدارة المحدد وتعليمات المشروع أولًا. نفذ الدفعة المحددة فقط. شخّص سبب الإخفاق قبل الإصلاح، واستخدم اختبارات ارتداد ذات معنى للأعطال حيث يمكن أتمتتها، ثم سجل تحقق ما بعد الإصلاح.

- لا تغير الحالة إلى `verified` ولا تغلق الإدارة بنفسك.
- لا تسجل نجاحًا إذا لم تنفذ الحالة. سجل المانع وما يلزم لإزالته.
- لا توسع النطاق بصمت عند اكتشاف مشكلة في مكون مشترك؛ وثق التأثير والملفات والاختبارات المطلوبة قبل متابعة العمل الذي يعتمد على توسيع النطاق.
- لا تستبدل إعدادات قاعدة البيانات لتجاوز إخفاق البيئة، ولا تنفذ عمليات تمحو بيانات قائمة دون تفويض صريح. استخدم بيئة وبيانات اختبار معزولة.
- شغل فحوص الصياغة والاختبارات المناسبة للتغيير. عند تعديل أي `.js` أو `.css` أو `.scss` شغل `npm run build` وسجل نتيجته.
- راجع البساطة والأمان وحدود المستأجرين في الإصلاحات، دون إعادة هيكلة غير مطلوبة.
- في نهاية الدفعة حدّث الحالات وأرفق الملفات المعدلة والأوامر والنتائج والموانع والمخاطر والدفعة التالية المقترحة. لا تكتف بعبارة «تم الحل».

## بوابة اعتماد الإدارة

يتحقق Codex من الآتي ويسجل الأدلة في ملف الإدارة:

1. مطابقة الحالات للنطاق الفعلي وبلاغات الـtester المتعلقة به، وقراءة أحدث البلاغات قبل الإغلاق.
2. مراجعة الملفات الفعلية والفروق كاملة، بما فيها الملفات الجديدة والتغييرات السابقة، دون الاعتماد على تقرير Gemini وحده.
3. إعادة تنفيذ الحالات المنطبقة بصورة مستقلة، وتحقق الصلاحيات والعزل والسيناريوهات السلبية والارتداد.
4. نجاح الاختبارات وفحوص الصياغة والبناء المطلوبة، والتحقق الفعلي من الواجهة للحالات البصرية والسلوكية.
5. عدم بقاء أي حالة `not_run` أو `failed` أو `blocked` أو `reopened` أو بانتظار المراجعة، وعدم وجود مشكلة معروفة غير محسومة داخل النطاق. توثيق سبب كل `not_applicable`.
6. تسجيل مرجع الكود النهائي والبيئة والتغطية والنتائج والقيود واسم المراجع وتاريخ القبول. أي تغيير مؤثر لاحقًا يعيد فتح الحالات المتأثرة.

`production_ready` تعني أن النطاق المحدد اجتاز التحقق الموثق على المرجع والبيئة المسجلين. لا تعني ضمانًا مطلقًا لغياب كل عيب محتمل، ولا تنفذ نشرًا تلقائيًا للإنتاج. إذا تعذر اختبار جزء مطلوب تظل الإدارة مفتوحة ويذكر السبب.
