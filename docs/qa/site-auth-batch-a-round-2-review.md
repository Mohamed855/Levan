## A2-01 — استهلاك recovery code غير محمي من طلبين متداخلين

**P1 — مانع اعتماد 2FA-09، ويؤثر في موثوقية 2FA-10/16.**

المواضع: `ResolveTwoFactorLogin.php:39` يسترجع المستخدم، و`:91` يقرأ أكواد الاسترجاع من كائن المستخدم الموجود، ثم `:108` يستدعي `PersistAuthenticationStateAction::replaceRecoveryCodes` الذي يحفظ القائمة دون قفل أو شرط يضمن أن الكود لم يُستهلك منذ قراءته.

إعادة الإنتاج المستقلة في Admin ثم Tenant:

1. مستخدم مؤكد 2FA له recovery code واحد اصطناعي.
2. تحميل كائنين لنفس صف المستخدم **قبل** استهلاك الكود، لمحاكاة الترتيب: طلب A يقرأ، طلب B يقرأ، A يحفظ، B يكمل.
3. تمرير الكود إلى `consumeRecoveryCode` مع نسخة A: يستهلكه وتصبح القائمة المحفوظة فارغة، وهو مثبت بالاختبار.
4. تمرير نفس الكود مع نسخة B: **لا يرفضه، رغم استهلاكه بالفعل**. الاختباران المتوقع فيهما `ValidationException` فشلا.

حدود الدليل: هذه إعادة إنتاج حتمية لتداخل القراءة والحفظ عند دالة الاستهلاك، وليست تجربة طلبَي HTTP متزامنين أو إثبات حادثة على بيئة فعلية. لكنها تثبت أن منع التكرار التسلسلي في الحزمة لا يكفي لضمان استهلاك مرة واحدة عند التزامن؛ مسار `verify` يمرر المستخدم الذي استرجعه قبل الاستهلاك.

**المطلوب من Gemini:** اجعل قراءة أهلية الحساب/قائمة الأكواد واستهلاك الكود عملية ذرية على الاتصال الصحيح للمستخدم؛ أعد القراءة داخل المعاملة/القفل أو استخدم تحديثًا مشروطًا مكافئًا، وارفض الخاسر دون تسجيل الدخول أو إرجاع الأكواد الأخرى. احفظ الأكواد مشفرة. لا تعتمد قفل session واحدة لأن محاولتين قد تأتيان من جلستين مختلفتين. راجع أثر regenerate/disable المتزامن أيضًا.

**القبول:** كود واحد مع محاولتين متداخلتين لا يكمل إلا محاولة واحدة؛ الأخرى مرفوضة؛ لا فقد للأكواد المتبقية ولا عودة كود ملغى. اختبر Admin وTenant مع قاعدة اختبار تدعم آلية التزامن المستخدمة، وأبقِ اختبارات التكرار التسلسلي.

## A2-02 — زر تأكيد إعداد Tenant يظل معطلًا بعد رفض الرمز

**P1 — مانع اعتماد 2FA-14 واستكمال 2FA-13.**

المواضع:

- `resources/views/tenant/auth/two-factor-settings.blade.php:144`: نموذج `data-validation-submit="ajax"`.
- `resources/assets/js/shared/form-validation.js:2266`: يضع زر الإرسال في حالة تحميل؛ `setButtonLoading` يعطله ويعطل التفاعل.
- المعالج المشترك بعد نجاح تحقق الشكل يطلق `formValidationPassed` ثم يعيد `isSubmitting=false` لأسلوب AJAX، لكنه لا يعيد الزر لحالته.
- معالج `formValidationPassed` في صفحة Tenant عند `:226` يرسل طلب التأكيد. مسار الخطأ عند `:249` يعرض خطأ الحقل وToastr، **ولا يستدعي إعادة الزر لحالته** أو يعالج اكتمال الطلب لذلك.

الفحص المستقل شغّل معالج submit و`setButtonLoading` الفعليين ومعالج AJAX الفعلي المستخرج من الصفحة، مع نجاح تحقق الشكل ورد خطأ تأكيد اصطناعي من الخادم. النتيجة:

```text
serverValidationErrorDisplayed: synthetic invalid TOTP
isSubmitting: false
buttonDisabledAfter422: true
buttonLoadingAfter422: true
retryAvailable: false
```

حدود الدليل: لا يوجد متصفح في هذا الفحص؛ عُزلت خدمات الحقول وAJAX. مصدر `setFieldError` راجِع أيضًا: يعرض خطأ الحقل ولا يعيد زر الإرسال لحالته. لا يُعد فحص Feature لرمز خاطئ/صحيح إثباتًا لقابلية النقر في الصفحة.

**المطلوب من Gemini:** استعد حالة الزر في اكتمال AJAX للفشل ونجاح التأكيد حسب حالة الصفحة، باستخدام واجهة loading المشتركة، مع منع التكرار. لا تعطل shared validation ولا تتجاوز التحقق الفعلي.

**القبول:** من نفس صفحة الإعداد: رمز من 6 أرقام لكنه خاطئ → 422 ورسالة → الزر قابل للمحاولة → رمز صحيح → نجاح دون reload. كرر بفشل شبكة وبإعادة فتح الإعداد وباستخدام Enter، ثم تحقق من Admin كتراجع للواجهة المشتركة. احفظ Network ولقطة/تسجيل للزر بعد الخطأ.

## A2-03 — دليل المتصفح لا ينفذ سلسلة Submit الحقيقية

**P1 — مانع اعتماد سلوك المتصفح في 2FA-01/02/07/08/13/14.**

قراءة `puppeteer_suite.cjs` و`render_views.php` أثبتت الآتي:

- يولد `render_views.php` HTML مباشرة من view؛ لا يزور GET challenge عبر password step/controller بجلسة مصادقة معلقة حقيقية.
- السيرفر التجريبي على 8199 يخدم HTML محفوظًا وأصولًا ثابتة، ولا يعالج مسارات Laravel أو validation أو challenge POST.
- فحص Enter يضيف listener لـsubmit ويستدعي `preventDefault()` ويعتبر وصول الحدث نجاحًا. هذا يثبت وصول حدث، ولا يثبت POST validation ثم POST challenge وقبول الرمز وتجديد session.
- لا اختبار نقر مزدوج أو دورة خطأ → تصحيح حقيقية، ولا إعدادات 2FA أو QR أو تأكيد في هذا السكربت.
- فحص التبديل يبحث عن `#codeGroup` و`#recoveryGroup`، بينما القالب يستخدم `#codeInputsWrapper` و`#recoveryWrapper`. السجل نفسه يعرض `Code group hidden: undefined`؛ و`!undefined` جعل فحص ظهور recovery يبدو صحيحًا.
- شروط PASS/FAIL مجرد رسائل؛ لا asserts توقف الاختبار، وcatch يسجل الخطأ دون exit غير صفري. لذلك جملة `ALL BROWSER PROBES COMPLETED SUCCESSFULLY` ليست معيار نجاح للحالات.
- لقطة باسم `tenant_desktop_recovery.png` بقيت بعرض 320px من آخر viewport؛ الاسم لا يثبت أن recovery اختُبر على desktop. قياسات الستة أحجام في السجل تخص وضع TOTP قبل التبديل.

**ما يُحسب من الدليل:** هو دليل متصفح على HTML مولد، مفيد لوجود حقل واحد وبعض القياسات والكتابة واللصق ونقل التركيز. لقطات Admin desktop وTenant 320 التي فُحصت تظهر ترتيب الرجوع يمين/التبديل يسار دون العيب القديم الظاهر. لا تُلغى هذه النتيجة الجزئية بسبب نقص E2E.

**المطلوب من Gemini:** اختبر بيئة Laravel محلية معزولة عبر routes الحقيقية وCSRF/session والأصول الفعلية. سجل POST التحقق وPOST التحدي وعددهما ونتائجهما، واضغط click/Enter/double-click، وأعد المحاولة بعد الخطأ في الوضعين. صحح selectors، وأضف asserts واكشف console/network failures وأعد exit غير صفري عند فشل شرط. اختبر كلا الوضعين عبر مصفوفة الأحجام وhover/focus، وارتداد موضع الرجوع في صفحات auth الأخرى. لا تنسب نتيجة submit ناجح إلى فحص يمنع submit النهائي.

## A2-04 — اختبار المستأجرين لا يثبت قاعدتين أو numeric ID متطابقًا

**P1 — نقص دليل 2FA-21/22؛ ليس إثباتًا لاختراق عزل الإنتاج.**

في `TwoFactorAuthenticationBatchATest.php:28` أُلغيت tenancy bootstrappers. تغيير `tenancy()->initialize(A/B)` لا يبدل اتصال SQLite الوحيد في هذا الإعداد. وفي `:554` و`:569` تمرر `id=1` عبر `User::create` رغم أن `id` ليس ضمن fillable.

الفحص المستقل أعاد نفس إنشاء المستخدمين وأثبت:

- الاتصال PDO نفسه في A وB.
- معرفا المستخدمين مختلفان فعليًا، وليس كلاهما 1.
- كلا المستخدمين مرئيان في جدول users نفسه.

بالإضافة إلى ذلك، `test_admin_and_tenant_session_isolation` يرسل `login.id=1` دون إنشاء حسابَي Admin وTenant القابلين للمصادقة في الاختبار نفسه. قبول رفض الطلب في هذا السيناريو لا يثبت التصادم المقصود وحده.

**المطلوب:** استخدم قاعدتي اختبار مستقلتين أو bootstrapper اختبار يبدلهما مع إثبات اختلاف الاتصال/البيانات. ثبّت ID=1 فعليًا في كل قاعدة وassert عليه قبل التنفيذ، وأنشئ حساب Admin=1 أيضًا عند اختبار cross-guard. اختبر كلا الاتجاهين مع رمز صالح للحساب الذي لا يجب دخوله، وتحقق من هوية المستخدم المتصل وحفظ الأكواد في قاعدته الصحيحة. لا تضعف شروط الرفض ولا تستخدم بيانات العمل الفعلية.

## A2-05 — Domain: فصل اختبار HTTP عن متصفح/DNS

**القرار: سبب غياب DNS لا يمنع Feature tests، بينما دليل المتصفح على domain ما زال غير منفذ.**

أضاف Codex fixture نطاق اصطناعي `review-auth.example.test` وسجل domain مع tenant داخل الذاكرة، ثم استخدم URL كاملًا في Feature requests دون DNS أو hosts. نجح:

1. GET challenge أعاد 200 وform action على نفس نطاق المستأجر.
2. resolver حدد tenant المقصود.
3. POST إلى form-validation نجح.
4. POST recovery صالح أكمل المصادقة ووجه إلى `/dashboard` على النطاق نفسه.

هذا فحص توجيه/جلسة/تحقق/إكمال داخل HTTP kernel وبـbootstrappers معزولة، وليس اختبار DNS/TLS أو كوكيز المتصفح أو تبديل قاعدتين فعليتين. لا يُستخدم لإغلاق المتغير الكامل.

**المطلوب:** نفذ بقية مصفوفة HTTP للدومين الآن، وحدد الجزء المتعذر بدقة كـ`TENANT-DOMAIN/BROWSER`، مع بيئة المضيف والكوكيز المطلوبة. وفر ربط مضيف محلي داخل بيئة المتصفح المعزولة دون اشتراط تغيير جهاز المستخدم أو DNS خارجي إذا لم يكن ضروريًا. لا تجعل blocked مقتصرًا على 01..08 بينما بقية الحالات ذات domain variants غير منفذة.

| 2FA-20 | GET بلا id يرد للـlogin، والسياق الناقص يرفض | deleted user، secret غير قابل للفك، انتهاء الجلسة والاستجابة الآمنة في اللوحتين |
| 2FA-21 | فحوص guard الصارمة وR1 تعمل | حسابان فعليان متطابقا ID مع variants المتصفح/تبويبين |
| 2FA-22 | tenant binding المفقود/المختلف يرفض في الاختبارات الحالية | **A2-04: اختبار القاعدتين الحالي لا يثبت ادعاءه**؛ path/domain/hint |
| 2FA-23 | inactive في النطاقين وunconfirmed Admin مرفوضون | بقية تغيرات الحالة بعد password step وGET/POST في Tenant |
| 2FA-24 | المحاولة السادسة محظورة في النطاقين | انتهاء فترة الحظر، session ID قبل/بعد، remember true/false، الوجهة والتنظيف الكامل |

## تسليم الجولة الثالثة إلى Gemini

1. أصلح A2-01 وA2-02 أولًا، مع regression مناسب لا يكتفي بالمصدر أو نتيجة backend.
2. أصلح دقة harness والاختبارات في A2-03 وA2-04، ثم نفذ المتغيرات الناقصة المبينة في الجدول. لا تطلب إعادة كل ما نجح دون سبب؛ أعد ما تأثر بالإصلاح وغطِّ الناقص.
3. افصل domain HTTP عن browser وفق A2-05، وسجل blocked فقط للجزء المتعذر مع السبب الفعلي.
4. صحح محاولة 2 بإضافة توضيح مؤرخ: القياسات كانت على HTML محفوظ، Enter منع الإرسال، معرفا المستأجرين لم يكونا متطابقين في قاعدتين. احتفظ بالسجلات القديمة ولا تحول الاستنتاجات القديمة إلى أدلة تنفيذ.
5. سجل hash/commit الفعلي بعد التعديل، ونتائج الحالات والأوامر والـvariants دون كلمة «تغطية كاملة» إن بقي جزء غير منفذ.
6. لا تبدأ B ولا توسع العمل إلى تقرير البنود الـ24 أو المزادات ضمن تسليم auth هذا. التصحيح محصور في الدفعة A وآثار مكوناتها المشتركة.
