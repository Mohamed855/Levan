## النتائج حسب الأهمية

### R01 — P1، باقية/A02: إعادة ضبط كلمة مرور مستخدم Tenant دون تفويض للعملية

- المسار: `routes/admin.php:58`، داخل المجموعة المركزية المسجلة حاليًا تحت `superadmin`.
- التنفيذ: `app/Http/Controllers/Tenants/Auth/NewPasswordController.php:91-97` يقرأ `tenant_id` من المدخلات ويمرر البريد وكلمة المرور إلى `executeForTenant`.
- `app/Http/Requests/Tenants/Auth/ResetTenantPasswordRequest.php:12-22` يسمح دائمًا وtoken اختياري، ولا يتحقق من tenant_id أو صلاحية إدارة حساب ذلك المستأجر.
- `app/Actions/Tenants/Auth/ResetTenantPasswordAction.php:32-39` يهيئ المستأجر المدخل ويغير كلمة المرور مباشرة.

النتيجة: حساب Admin مستوفٍ middleware العامة يستطيع استهداف مستخدم Tenant معلوم البريد دون permission متخصصة أو token/OTP خاص بالاستعادة. لا يكفي `auth:admin` لتفويض هذا الأثر عبر الحدود. لم أنفذ تغيير كلمة مرور أثناء المراجعة.

**القبول المطلوب:** فصل مسار استعادة المستخدم العام عن إجراء إداري مصرح به، مع FormRequest/Policy مخصصين وتحقق tenant ownership/audit؛ اختبار admin محدود يرفض، وتدفق OTP/token لا يقبل إعادة الاستخدام.

### R02 — P1، باقية مع مشكلة جديدة/T06: استبدال ملفات العقار ما زال يمكن أن يفقد البيانات

`app/Actions/Tenants/Properties/UpdatePropertyAction.php:197-215` يحذف الملف القديم من التخزين قبل تخزين الوثيقة البديلة. إذا فشل الرفع أو أي كتابة لاحقة، rollback يعيد سجل المرفق القديم لكن لا يعيد bytes المحذوفة.

كذلك تنظيف الملفات المؤجل الجديد عند `:233-239` داخل نفس try المحيط بالمعاملة: لو نجح commit ثم رمى حذف القديم exception، يدخل catch وينظف الملفات الجديدة رغم أن DB تشير إليها بالفعل.

**القبول المطلوب:** تخزين الجديد ثم commit، وبعده cleanup للقديم مستقل وقابل للمحاولة؛ rollback cleanup للنطاق الذي لم ينجح فقط. اختبار فشل تخزين البديل وفشل تنظيف القديم بعد commit، مع التحقق من bytes وسجلات DB معًا.

### R03 — P1، جديدة/T05: منطق Edit الإسناد لا يبدأ بسبب معرّف الفورم

`resources/views/tenant/assignments/partials/_form.blade.php:23` يولد `assignment-edit-form` في التعديل، بينما `resources/assets/js/tenant/assignments/create.js:4-5` يبحث عن `assignment-create-form` فقط ثم يخرج مبكرًا. صفحة Edit تحمل السكربت نفسه.

النتيجة: لا يعمل تزامن اختيار العقارات إلى hidden inputs، ولا إزالة البطاقات أو تحديث مراجعة البيانات التي يديرها السكربت. مشاركة ملف Blade وحدها لم تحقق تكافؤ الوظيفة.

**القبول المطلوب:** تهيئة كلتا الحالتين بعقد DOM مشترك، واختبار متصفح يفتح Edit ويضيف ويحذف عقارًا ويتحقق من payload ومن نتيجة الحفظ والمراجعة.

### R04 — P1، جديدة/T05: تحديث الإسناد يكسر انتماء عقارات المزاد

`app/Actions/Tenants/Assignments/UpdateAssignmentAction.php:35-45` يفصل كل عقار لم يعد في الاختيار، ثم يربط IDs الجديدة مباشرة، بلا منع فصل عقار داخل مزاد وبلا lock وإعادة فحص الإتاحة داخل transaction.

سيناريو: عقار مرتبط بمزاد للإسناد A يُفصل من A، فيبقى `auction.assignment_id=A` بينما `property.assignment_id=null`. كذلك طلبان اجتازا validation لعقار متاح يمكن لآخرهما أن ينقله من إسناد الأول. فحص FormRequest السابق لا يغلق نافذة التزامن.

**القبول المطلوب:** قفل السجلات اللازمة وإعادة فحص الإتاحة وقواعد فصل العقارات داخل العملية؛ اختبار منع الفصل أثناء وجود مزاد واختبار طلبين متنافسين على العقار نفسه.

### R05 — P1، باقية/T15: الحذف الجماعي يتجاوز قواعد الحذف الفردي

`app/Actions/Tenants/MassDelete/DeleteTenantRecordsAction.php:15-17` ينفذ `$record->delete()` مباشرة. في المقابل، `app/Services/Tenants/Assignments/AssignmentService.php:96` و`app/Services/Tenants/Properties/PropertyService.php:42` تمنعان حذف بعض السجلات المرتبطة في التدفق الفردي. Policies لا تعيد هذه القيود.

النتيجة: يمكن حذف إسناد له عقارات/مزادات أو عقار مرتبط بمزاد من المسار الجماعي رغم رفض المسار الفردي للعملية نفسها.

**القبول المطلوب:** توحيد domain deletion operation وإعادة استخدامها بعد Policy لكل row، واختبار السجل نفسه عبر single/mass وإثبات الرفض المتسق ونتيجة batch الواضحة.

### R06 — P1، باقية/S03: هوية مسودة Tenant تُنسب إلى Admin عند وجود الجلستين

`app/Services/Shared/Wizard/WizardDraftService.php:152-162` يختار guard الإداري متى وُجدت جلسة Admin، حتى لو كان الطلب لمسار Tenant. الاختيار نفسه موجود في `app/Http/Middleware/DiscardCompletedWizardDraft.php:23`.

النتيجة: مسودات مستخدمي Tenant على المتصفح نفسه تُحفظ بهوية Admin؛ تبديل مستخدم Tenant داخل قاعدة المستأجر نفسها مع بقاء جلسة Admin قد يسترجع مسودة المستخدم السابق.

**القبول المطلوب:** تحديد guard من route/boundary المقصود وتوحيد identity في الحفظ والاسترجاع والملفات والحذف؛ اختبار admin+tenant sessions ومستخدمين مختلفين داخل المستأجر نفسه.

### R07 — P1، باقية/S03: حفظ المسودة قد يفقد الملف القديم أو يعيد عناصر محذوفة

`app/Services/Shared/Wizard/WizardDraftService.php:253-254` يحذف ملف المسودة السابق أثناء merge، بينما `draft->save()` يأتي لاحقًا في `:46`. فشل حفظ DB يترك metadata قديمة لملف محذوف وملفًا جديدًا يتيمًا.

وفي `:37-40` يستخدم `array_replace_recursive` لمصفوفات البيانات. حفظ `[A,B]` ثم حذف B وحفظ `[A]` لا يزيل الفهرس القديم؛ النتيجة المسترجعة ما زالت `[A,B]`. تمت إعادة إنتاج دلالة الدمج مباشرة في PHP دون قاعدة بيانات.

**القبول المطلوب:** دورة تخزين تعوض الفشل، وحسم replace-vs-merge للمجموعات المرسلة مع دعم المصفوفة الفارغة والحذف الصريح؛ اختبار حذف مالك/وحدة ثم استرجاع وحفظ نهائي دون إحيائه.

### R08 — P1، باقية/S03: تجاهل المسودة يعتبر HTTP500 نجاحًا

`resources/assets/js/shared/form-validation.js:668-682` ينتظر fetch الخاص بـDELETE لكنه لا يفحص `response.ok`. فرع «تجاهل» في الاسترجاع يتابع فتح النموذج رغم رفض الحذف من السيرفر.

النتيجة: يبدأ المستخدم نموذجًا جديدًا بينما المسودة والملفات القديمة باقية؛ وقد يندمج الحفظ الجديد معها. أُعيد إنتاج الدالة مع fetch يعيد500؛ انتهت بنجاح بدل الرفض.

**القبول المطلوب:** التحقق من response وعدم فتح نموذج جديد حتى نجاح discard، وإظهار retry عند الفشل؛ اختبار500/403 وفشل شبكة وحذف ناجح.

### R09 — P1، باقية/S03: مرفقات المسودة بلا تحقق أنواع/أحجام المورد

`app/Http/Requests/Shared/Wizard/StoreWizardDraftRequest.php:16-22` يتحقق فقط من `resource_key` و`step`، بينما `WizardDraftService.php:43` يخزن `allFiles()` قبل المرور بالـFormRequest النهائي.

النتيجة: يستطيع مستخدم مسجل رفع أنواع وأعداد وأحجام خارج سياسة ملفات المورد ضمن الحدود العامة لـPHP، حتى إن لم يرسل Create النهائي. قواعد final submit لا تحمي التخزين التدريجي.

**القبول المطلوب:** عقد file-only خاص بالمسودة مرتبط بمورد مسموح، مع ownership وMIME/size/count/quota؛ لا أفرض اكتمال حقول Create على الحفظ كمسودة.

### R10 — P1، جديدة في working tree: تحويل روابط Admin القديمة إلى عنوان نسبي متكرر

`routes/admin.php:284` يستخدم `Route::redirect('admin/{any}', 'superadmin/{any}')` دون `/` في بداية الوجهة. استدعاء RedirectController على route الفعلي أعاد `Location: superadmin/users` للعنوان `/admin/users`.

المتصفح يحل هذا كـ`/admin/superadmin/users` ثم يدخل في تحويلات متزايدة بدل الوصول إلى `/superadmin/users`. كذلك302 لا يحافظ على method/body للعمليات القديمة.

**القبول المطلوب:** وجهة مطلقة داخل الموقع وعقد توافق واضح لطلبات القراءة والكتابة؛ اختبارات redirect للـnested URLs وأسماء routes وطلبات POST القديمة. تغيير prefix ليس بديلًا عن استخدام route helpers في JS.

### R11 — P1، باقية/T10: مسار تجديد النطاق لا يزوّد handler بمعامله الإلزامي

`routes/tenant.php:197` يعرّف POST للتجديد بلا `{domain}`، بينما `app/Http/Controllers/Tenants/Domains/RenewalDomainController.php:30` يتطلب `$domain` دون FormRequest. Laravel لا يربط body field تلقائيًا بمعامل primitive.

النتيجة: `ArgumentCountError` بدل التجديد؛ إثبات التوقيع والجرد وReflection لا يحتاج طلبًا إلى مزود الدومينات.

**القبول المطلوب:** Request متخصص ومدخل domain معتمد والتحقق من ownership، ثم service/gateway؛ اختبار رفض نطاق غير مملوك ونجاح المسار الصحيح بمزود مزيف.

### R12 — P2، باقية/T08: أخطاء مولّد التقارير ما زالت تُعرض خامًا

`app/Jobs/Tenants/Auctions/GenerateAuctionReportsJob.php:160` يخزن `$e->getMessage()`، و`app/Http/Controllers/Tenants/Auctions/AuctionReportController.php:44` يعيدها في status. تستخدمها واجهة Show وDataTable.

إصلاح رسالة catch الخاصة بـretry لا يمنع كشف مسار داخلي أو تفاصيل command عند فشل renderer لاحقًا.

**القبول المطلوب:** error code/message عامة للمستخدم وlog داخلي مفصل؛ اختبار فشل renderer يحوي تفاصيل داخلية لا تظهر في status/Show/DataTable.

### R13 — P2، باقية/A21: مستخدم يملك إنشاء FAQ يحصل على403 عند الحفظ

`app/Http/Requests/Admin/FaqRequest.php:4` يشترط `faqs.edit` حتى في Store، بينما Policy وزر الإنشاء يعتمدان `faqs.create`. مستخدم يملك create فقط يفتح الصفحة ثم يُرفض عند الحفظ. أُثبت قرار authorize باختبار PHP مع مستخدم مزيف دون DB.

**القبول المطلوب:** فصل Store/Update authorization واختبار create-only وedit-only وتوافق policy والواجهة وFormRequest.

## صلاحية أدلة الاختبار

- اختبارات AssignmentFormParityTest وPropertyFormParityTest الجديدة تفحص نصوص الملفات؛ لا ترندر Edit ولا تشغل JavaScript ولا تختبر update/rollback. لذلك لا يمكن أن تكشف R02/R03.
- AuctionReportStatusProgressTest يفحص موديلًا غير محفوظ وrules فارغة؛ لا يثبت تفويض المستخدم أو queue lifecycle.
- محاولة PHPUnit الحالية انتهت بـexit1 و`Cannot open bootstrap script`، بما فيها محاولة تحديد bootstrap صراحة. الملف ظهر موجودًا لفحص PHP، لذلك لا أجزم بأنه محذوف؛ المشكلة الحالية هي تعذر تحميله بواسطة runner. لا أستعمل نتائج الاختبارات التاريخية كدليل نجاح حالي.
- لم أشغل Feature/DB suite لعدم التحقق من قاعدة اختبار منفصلة، ولم أشغل migrations.
- `git diff --check` أظهر blank line زائدة في آخر routes/admin.php؛ هذه ملاحظة بسيطة وليست سبب الحكم الأساسي.
- public/build.zip يحتوي build assets حسب الجرد المحدود؛ لم أعتبر وجود الأرشيف دليلًا على build ناجح أو مراجعة أمنية شاملة لكل محتواه.
