# خطة مطابقة جميع إدارات Admin وTenant مع Golden Pattern

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task, or `subagent-driven-development` if parallel execution is explicitly selected. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** أريد مطابقة كل صفحة ووظيفة نشطة في لوحتي Admin وTenant مع Golden Pattern، مع الحفاظ على قواعد المجال والعقود العاملة، وإثبات المطابقة باختبارات وظيفية ومعاينة بصرية.

**Architecture:** سأعالج النظام كإدارات كاملة تمر عبر Route → Guard/Middleware → Controller → FormRequest/Policy → Action/Service/Gateway → UI → Tests. سأصلح المكونات المشتركة أولًا، ثم أعالج فجوات كل إدارة دون إعادة بناء الأجزاء السليمة أو إعادة إدارات قديمة إلى النظام.

**Tech Stack:** Laravel 11، PHP 8.2+، Blade، Bootstrap 5، SCSS/Vite، jQuery، BS-Stepper، Select2، SweetAlert2، Yajra DataTables، multi-tenancy بحدود Central/Tenant.

**Spec:** [Golden Pattern](../../architecture/golden-pattern.md)، و[AGENTS.md](../../../AGENTS.md)، وطلب مقارنة جميع صفحات اللوحتين وإعداد خطة تنفيذ مفصلة. هذه الوثيقة وملحقاتها هي خطة عمل مكتوبة بصوت صاحب المشروع؛ لا تعني اعتماد تغييرات في قواعد المجال خارج الطلب.

**تاريخ الفحص:** 29 أكتوبر 2026، Africa/Cairo. **مرجع Git:** `3a6af9f75e691c27c7a4016b4fa3224921a47062` مع تغييرات محلية موجودة قبل بدء الفحص. الأدلة تخص نسخة العمل وقت الفحص، وليست شهادة على commit نظيف.

**متابعة التنفيذ الفعلي:** [سجل التنفيذ والأدلة والبنود المتبقية](../../baselines/golden-pattern-execution.md). حالة الخطة قيد التنفيذ؛ لا تُستنتج المطابقة من بنود الخطة وحدها.

## 2. النطاق الفعلي والمقارنة التي بنيت عليها الخطة

- استخرجت routes الفعلية بواسطة `php artisan route:list --json`، ثم جمعت تكرارات الدومينات ومسارات Tenant من نوع domain/path تحت boundary + route name + HTTP method + handler.
- الجرد الخام في نطاق Controllers الخاصة بـAdmin/Tenants/Shared يحتوي **937 نسخة ربط**. بعد التطبيع توجد **371 خانة**: **370 عقدًا داخل اللوحتين**، وواحد `site.form-validation` خارج نطاق اللوحتين وموسوم `OUT-site`.
- عقود اللوحتين: **177 Admin و193 Tenant**، تتصل بـ**338 handler مختلفًا و69 Controller class**. هذه أعداد عقود HTTP، وليست أعداد صفحات أو إدارات.
- كل عقد من العقود الـ370 مرتبط بمالك تنفيذ `Axx` أو `Txx` أو `Sxx` داخل خريطة التغطية. استخدمت **21 حزمة Admin و15 حزمة Tenant** لتقسيم التنفيذ؛ بعض الحزم تجمع قدرات مترابطة، وبعضها يفصل الأدوار عن المستخدمين. هذه الحزم لا تعيد تعريف أعداد عائلات الإدارات القديمة تلقائيًا.
- أضفت root redirect في `routes/tenant.php:252` كحالة تنقل يجب اختبارها في domain/path؛ هو Closure للانتقال إلى dashboard، لذلك لا يدخل في جرد Controller handlers.
- جرد الصفحات الآلي يحتوي **80 مرجع view مباشرًا** في Controllers. لا أعتبر هذا عدد الصفحات النهائي؛ بعض الصفحات تمر عبر view ديناميكي أو خدمة أو partial أو تنزيل، وتفصلها ملحقات الإدارات. اختلاف أسماء view في aliases لا يعني وجود صفحة جديدة.
- الفحص هنا ساكن للكود مع تشغيل اختبارات Unit محددة لا تحتاج قاعدة بيانات. لم أسجل دخولًا لكل صفحة، ولم أنفذ رحلة CRUD كاملة أو screenshot comparison. أضع التحقق الوظيفي والبصري ضمن شروط القبول، ولا أصف layout بأنه مطابق اعتمادًا على أسماء classes فقط.
- لن أعيد فرق العمل أو التحصيلات أو إدارات العملاء القديمة أو الإعدادات العامة أو شاشات permissions/version إلى قائمة الإدارات لمجرد وجود ملفاتها. أعتمد الوصول الفعلي من route نشط، وأعالج الروابط المعطلة إليها داخل الصفحات النشطة.
- سأحافظ على aliases الحالية، ومنها `admin.companies.*` التي تصل إلى ClientController، إلى أن يكون لها استخدام معروف وخطة توافق وموعد إزالة موثق؛ لن أحذفها لمجرد تغيير اسم الإدارة.

## 3. Global Constraints — قواعد ملزمة لكل مهمة

- ألتزم بتعليمات المستخدم و`AGENTS.md` أولًا، ثم Golden Pattern المكتوب، ثم أمثلة الإدارات. عند تعارض مثال أو خطة قديمة مع هذه القواعد أصلح المرجع ولا أنسخ المخالفة.
- أستخدم `auth:admin` للمركزي و`auth:tenant` للمستأجر، مع middleware تهيئة tenancy الفعلي. أي عبور من Tenant إلى Central يمر عبر Gateway صريح وسياق مستأجر؛ لا أعيد Central Eloquent Model إلى واجهة Tenant إذا كفت DTO/options.
- أحتفظ بمفاتيح DB والصلاحيات والأدوار والحالات الإنجليزية، وأستخدم الترجمة للعربية. لا أغير permission model الحالي أو أسماء routes ضمن إصلاح شكل الصفحة دون migration توافق مبررة.
- أستخدم `route()` للمركزي و`tenant_route_name()` للمستأجر، و`tasset()` لملفات Tenant، وعقد assets المركزي القائم؛ لا أبني tenant URLs باستخدام معرف المستأجر يدويًا.
- أضع `authorize/rules/messages/attributes` في FormRequests الصحيحة. Request فارغ يثبت تسجيل الدخول وحده لا يثبت ملكية السجل أو صلاحية العملية. لا أكرر قواعد validation في JavaScript.
- أستخدم Policy مسجلة لكل سجل، وأتحقق من parent/subresource ownership، ومن Policy وقواعد المجال لكل عنصر في mass delete.
- أحافظ على Controllers نحيفة، وأضع المعاملات والملفات والعلاقات في Actions/Services؛ لا أضيف Repository عام أو abstractions بلا حاجة.
- أوحد Create/Edit في `partials/_form.blade.php` ومتغير `$is_edit`، وبنفس الخطوات والحقول. كل Create يدعم المسودة كاملة، وEdit لا يعرضها إلا بعقد مستقل مصرح به.
- النموذج أحادي الخطوة بلا stepper header أو review مصطنعة. متعدد الخطوات ينتهي بمراجعة كاملة العرض، وزر التالي/المراجعة متاح بصريًا ويتحقق عند الضغط من الخطوة الحالية فقط.
- أستخدم المكونات المشتركة لكل حقول النماذج؛ `x-filter.select` للفلاتر فقط. ألتزم بنصوص الأزرار الافتراضية، وأجمع المسودة والإجراء التالي داخل `d-flex gap-2`.
- أعرض جميع معاينات الملفات بـ`x-ui.file-card`/`x-ui.attachment-card`، `layout="card"` وبحجم `150×150` في Show/Edit/Review والرفع التدريجي.
- أضع الإحصائيات أولًا في Index، وزر الإضافة داخل DataTable toolbar فقط، وعمود الحالة قبل الإجراءات. النشاط boolean يستخدم السويتش المشترك؛ workflow status لا يتحول عشوائيًا إلى activity toggle.
- الأرشيف دون عناوين أو breadcrumbs أو إحصائيات، وله restore/force-delete Requests/Policies وعقد browser redirect/AJAX JSON الصحيح.
- لا أغير ملفات التعديلات المحلية السابقة ضمن هذه الخطة قبل مراجعة diff وفصل ما يخص المهمة. منها `ApproveTrialRequestAction.php` وملفات قواعد التسجيل واختباراتها التي كانت معدلة قبل الفحص.
- لا أعتمد placeholders أو TODOs كإنجاز. كل بند `not_applicable` له سبب وظيفي محدد، ولا أنشئ ملفات فارغة لاستكمال قائمة.
- بعد أي تعديل `.js/.css/.scss` أشغل `npm run build`. تعديل وثائق الخطة الحالية وحده لا يستدعي بناء assets.

## 7. قالب التنفيذ الإلزامي داخل كل حزمة

أطبق هذا التسلسل مع الخطوات الخاصة والملفات المحددة في الملحق، ولا أتعامل مع التحقق العام كبديل عن تفاصيل الإدارة:

- [ ] أفتح بطاقة الإدارة وأطابق routes/handlers/pages مع coverage الحالية، وأحدد الفرق عن snapshot دون حذف ما أضافه مستخدم آخر.
- [ ] أكتب اختبارًا للسلوك الناقص باسم يصفه، وأثبت فشله للسبب المقصود؛ مثال: فقد view، route name خاطئ، تسرب ownership، أو حذف يتجاوز invariant.
- [ ] أراجع FormRequest الحقيقي وPolicy المسجلة وguard وroute parameter وأحدد contract الإدخال والاستجابة قبل تعديل الواجهة.
- [ ] أصلح Action/Service/Gateway المطلوب، مع transaction/locking/afterCommit وتنظيف الملفات عند الحاجة؛ لا أنقل التعقيد من Controller إلى class شامل مبهم.
- [ ] أوصل الواجهة بالمكون المشترك وroute helper وDOM validation contract، مع إبقاء قيم السجل وold input والمسودة وفق الحالة.
- [ ] أختبر HTML redirect + flash وAJAX JSON/422/403 بحسب العملية، وTenant A/B والمالك الآخر والعلاقات الخارجية.
- [ ] أشغل اختبار الحزمة ثم العقود المشتركة المتأثرة فقط. أشغل build إذا عدلت assets.
- [ ] أراجع الصفحات بصريًا وأحفظ أدلة desktop/tablet/mobile، ثم أعيد اختبار رحلة المستخدم كاملة.
- [ ] أراجع diff والأمان وأحدث البطاقة بالحالة والأوامر والنتائج والـN/A؛ لا أضع Compliant مع فجوة غير مغلقة أو دليل غير منفذ.
- [ ] أسجل مجموعة التغييرات في commit مستقل بعد التحقق، دون stage شامل أو إدخال تغييرات المستخدم السابقة.

## 10. بوابات القبول التي لن أغلق الخطة بدونها

### G0 — قاعدة اختبار وجرد صحيحان

- [ ] إعداد Central/Tenant testing databases وأقراص fake/معزولة وcache/session/queue/mail test drivers، مع منع اختبار مدمر إذا اتصل بقاعدة غير اختبارية.
- [ ] تحديث inventory tests لتعكس الإدارات النشطة وإضافات FAQ/AuctionTemplates/Clients/report workflows، واستبعاد legacy بدليل runtime.
- [ ] كل handler نشط موجود، وكل mutation متخصصة تستقبل FormRequest حقيقيًا أو استثناء authentication معلنًا ومختبرًا؛ تضم العقود Controllers المشتركة والـinvokable أيضًا.
- [ ] لا يكتفي اختبار الجرد بالبحث عن أسماء ملفات أو كلمة Compliant؛ يرتبط كل بند باختبار سلوك ودليل فعلي.

### G1 — قبول كل إدارة وظيفيًا

- [ ] guest، مستخدم بلا permission، مستخدم له permission على سجل داخل النطاق، وسجل خارجه، وحالة soft-deleted.
- [ ] GET للقراءة فقط؛ POST/PUT/PATCH/DELETE للعملية الصحيحة، مع CSRF وسلامة route parameters.
- [ ] index/create/edit/show والصفحات المتخصصة الحالية تعمل؛ صفحات غير مدعومة تظل N/A بسبب واضح.
- [ ] required/type/enum/unique/file/relation rules، و422/old input، مع عدم نسخ القواعد في JS.
- [ ] CRUD والآثار الجانبية والـfiles/drafts/archive/mass-delete/status حسب قدرات الإدارة، مع الحفاظ على workflow invariants.
- [ ] routes عبر domain وpath وcentral aliases الأساسية؛ أسماء الروابط في الصفحات لا تشير إلى تعريفات محذوفة.

### G2 — القبول البصري لكل صفحة

أراجع الصفحات المذكورة في كل ملحق، بما فيها الحالات الفارغة والمحملة بالأخطاء والصلاحيات المحدودة، عند عروض **1440 و1024 و390 بكسل** كأبعاد مراجعة عملية لهذه الخطة.

- [ ] Index يبدأ بالإحصائيات والفلاتر والجدول دون banner أو Add منفرد؛ الأزرار والصورة والكود والحالة بالترتيب الصحيح.
- [ ] Create/Edit لهما نفس الحقول والخطوات والتوزيع؛ النموذج الأحادي دون header، والمتعدد بمراجعة أخيرة، والأزرار بالنصوص الافتراضية.
- [ ] استرجاع draft وتجاهله ورفع ملف/حذفه وظهور file cards والمراجعة تعمل عند التفاعل؛ لا يكفي screenshot ثابت.
- [ ] Show بعموديه والمرفقات `150×150` والجداول التابعة، دون تحميل علاقات كبيرة بلا pagination.
- [ ] Archive جدول وفلاتر/أخطاء فقط؛ RTL والـsidebar والتمرير والخطوط والهوية وفق العقود المشتركة.
- [ ] كل اختيار Select2 وحقل تاريخ ورسالة خطأ accessible وfocus/keyboard يعمل؛ لا يوجد overflow أفقي للصفحة إلا داخل table-responsive عند الحاجة.
- [ ] أحفظ route + viewport + الحالة + صورة الدليل لكل صفحة في سجل QA مرتبط ببطاقة الإدارة؛ الحالات التي تحتاج بيانات أو مزود خارجي تذكر fixture/result صراحة.

### G3 — الأوامر النهائية بعد التنفيذ

بعد G0، أشغل اختبارات الإدارة المحددة في ملحقها أولًا، ثم العقود الأفقية المتأثرة؛ وفي النهاية:

```powershell
php artisan route:list --json
php artisan test --filter='ActiveRouteHandlerContractFeatureTest|ActiveControllerMutationBoundaryContractTest'
php artisan test --filter='GoldenPattern|DataTableContract|SharedFormValidation|CreateFormDraft|TenantCentralBoundary|MassDeletePolicy|TenantArchivePolicy'
php artisan test
npm run build
git diff --check
```

هذه أوامر قبول مستقبلية، وليست ادعاءً بأنها نُفذت أو نجحت أثناء إعداد الخطة. أوامر build/full tests تأتي على نسخة التنفيذ وبعد إعداد العزل، وتوثق مخرجاتها مع commit المحدد. Blade compilation وحده لا يغني عن rendered pages أو اختبار routes.

## 11. المخرج النهائي الذي أطلبه من التنفيذ

- [ ] كل route في coverage له إدارة/عقد مشترك وبطاقة حديثة، وكل صفحة نشطة لها نتيجة فحص ومعيار قبول محقق.
- [ ] كل إدارة لها scope وguard/routes وRequests وPolicy وAction/Service وModels/Enums/Jobs عند الحاجة وUI/tests مع ملفات صحيحة أو N/A مسبب.
- [ ] الأعطال المثبتة في المقارنة أغلقت، والاختبارات الحساسة لشكل المصدر استبدلت باختبارات عقد وسلوك دون إخفاء الخلل الحقيقي.
