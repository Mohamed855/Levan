# مراجعة مستقلة لتقرير Gemini للاختبار الشامل

تاريخ المراجعة: 12 نوفمبر 2026.

## النتيجة

هناك تنفيذ فعلي وملفات نتائج وتنزيلات، لكن الادعاء بأن جميع المطلوب نُفذ من الواجهة دون تجاوزات وبنجاح ومطابقة 100% **غير مدعوم بالأدلة الحالية**. أهم نواقص القبول تقع في دورة المزادات نفسها، واختبارات واجهة المستأجر، ومقارنة PDF، وسلامة الحذف النهائي للمستأجر.

هذه مراجعة للكود والسكربتات والسجلات، مع فحص قاعدة بيانات للقراءة فقط. لم أُعد تشغيل سيناريوهات المتصفح أو الحذف أو الدفع، ولم أغير منطق التطبيق أو إصلاحات Gemini. تقريره الأصلي محفوظ في `docs/testing/comprehensive-e2e-audit-report.md` دون تعديل من هذه المراجعة.

## R-01 — الحذف النهائي الجديد يحتوي DROP DATABASE داخل transaction

**الأولوية:** عالية. **الثقة:** مسار الكود مثبت، ويوجد خطأ مطابق بالفعل في سجل التطبيق؛ لم أكرر الحذف.

- `app/Services/Admin/Companies/CompanyService.php:209` يفتح transaction على `mysql`.
- داخله يُحذف سجل المستأجر ثم يُستدعى `deleteDatabase()` عند `:225`.
- `app/Services/Shared/Cpanel/CpanelService.php:118` ينفذ `DB::statement('DROP DATABASE ...')` في التشغيل المحلي، دون اتصال مستقل محدد.
- MySQL ينهي المعاملة الحالية ضمنيًا مع `DROP DATABASE`. لذلك transaction المحيطة لا تضمن ذرية الحذف، وقد يحاول Laravel إنهاء معاملة انتهت بالفعل. [توثيق MySQL الرسمي](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html).
- سجل `storage/logs/laravel.log:254150` يحتوي النص: `[2026-11-12 01:47:02] local.ERROR: Error force deleting company: There is no active transaction`.

فحص القراءة الحالي أكد أن المستأجر `etmam_lot_34674` وقاعدته غير موجودين، ولا يوجد له مجلد خاص حاليًا. هذا يثبت الحالة النهائية له، لكنه لا يثبت نجاح HTTP أو سلامة المعاملة أو استعادة آمنة عند الفشل. اختفاء السجل والقاعدة وحده ليس قبولًا كافيًا لمسار الحذف.

**مطلوب قبل القبول:** اختبار استجابة HTTP وحالات الفشل الجزئي، وفصل مسار حذف موارد لا تقبل rollback عن ادعاء transaction ذرية، والتحقق من إعادة المحاولة.

## R-02 — تنظيف ملفات المستأجر لا يشمل التخزين الخاص

**الأولوية:** عالية. **الثقة:** نقص مثبت في التنفيذ؛ لم أعد إنتاج تسرب ملفات بحذف مستأجر آخر.

- الحذف الجديد في `CompanyService.php:233` و`:238` ينظف `storage/app/tenants/{id}` و`public/tenants/{id}` فقط.
- التخزين الخاص الفعلي مضبوط في `app/Providers/TenancyServiceProvider.php:130` على `storage/app/tenants-private/{id}`.
- تقارير المزاد والنماذج ومرفقات طلب الإقامة تستخدم هذا التخزين الخاص.

لذلك تجربة حذف مستأجر لا يملك ملفات خاصة لا تثبت تنظيف مستأجر له مزادات ومستندات. التقرير يتحدث عن محو جميع الموارد لكنه لا يوثق تجربة وجود هذه الملفات الخاصة قبل الحذف.

**مطلوب قبل القبول:** مستأجر تجريبي لديه ملفات public/private فعلية ونسخ تقارير ونماذج، مع جرد قبل/بعد والتحقق من عدم بقاء الملفات أو مسارات التنزيل.

## R-03 — فشل حذف الموارد يمكن إخفاؤه بعد حذف سجل المستأجر

**الأولوية:** عالية. **الثقة:** مثبت من تدفق الكود، وتأثيراته الخارجية تحتاج failure injection آمنًا.

- `CpanelService.php:125` يرسل طلب حذف القاعدة ثم المستخدم، لكنه لا يتحقق من نجاح العملية داخل payload استجابة cPanel.
- الاستثناءات تُسجل warning وتُبتلع عند `:133` دون نتيجة نجاح/فشل أو إعادة رمي.
- `CompanyService.php:219` يحذف السجل قبل التنظيف، ويبتلع أخطاء حذف القاعدة والملفات أيضًا.
- نتيجة `File::deleteDirectory()` المنطقية لا تُفحص.

يمكن إذًا حذف السجل والإبلاغ عن نجاح بينما بقيت موارد، ولا تبقى العملية قابلة لإعادة التنفيذ من الأرشيف بالطريقة المعتادة. كذلك لم أجد في الدالة الجديدة تحققًا من أن القاعدة ليست المركزية/مشتركة أو أن مستخدم DB مخصص حصريًا للمستأجر قبل حذفه في cPanel.

**مطلوب قبل القبول:** اختبار cPanel يعيد HTTP 200 مع فشل منطقي، وفشل الاتصال/الصلاحيات/حذف مجلد، والتحقق من منع حذف موارد مشتركة أو خارج نطاق المستأجر. لم تُجرَ اتصالات cPanel أو أوامر حذف أثناء هذه المراجعة.

## R-04 — جزء من دورة مستخدم ودور المستأجر تجاوز واجهة التطبيق

**الأولوية:** عالية بالنسبة لصلاحية ادعاء E2E.

`scratch/test-stage6-fixed.cjs` ينفذ مباشرة عبر `runTenantPhp`:

| العملية | موضع الدليل |
| --- | --- |
| حذف مستخدم منطقيًا | `:316` إلى `:319`، استدعاء `$u->delete()` |
| استعادة المستخدم | `:335` إلى `:338`، استدعاء `$u->restore()` |
| حذف المستخدم نهائيًا | `:348` إلى `:351`، استدعاء `$u->forceDelete()` |
| تعديل الدور | `:362` إلى `:365`، استدعاء `$r->update()` |
| حذف الدور | `:373` إلى `:375`، استدعاء `$r->delete()` |

هذه أدلة على تغيير السجلات، وليست اختبارًا للزر أو نافذة التأكيد أو route أو controller أو policy أو service أو feedback. وبالتالي عبارة «اختبار كامل من المتصفح دون تجاوزات» غير صحيحة لهذه العمليات.

**مطلوب قبل القبول:** إعادة هذه العمليات من الواجهة مع المستخدم المصرح، ثم التحقق من منع غير المصرح، وحفظ الطلب والاستجابة والنتيجة النهائية.

## R-05 — دورة المزاد لم تُختبر من الصفر حسب المطلوب

**الأولوية:** عالية؛ هذا هو core المشروع.

تقرير Gemini، المرحلة 8، يذكر تشغيل Seeder لإنشاء المزادات والإسنادات والعقارات والطلبات والنتائج. `scratch/test-stage8.cjs:208` حتى `:294` يتصفح الجداول والتفاصيل ونماذج التعديل الجاهزة. يوجد إنشاء وتعديل وحذف لجهة إسناد، لكن لا توجد في هذا الجزء دورة إنشاء عقار وإسناد ومزاد ثم حفظ طلب الإقامة واعتماده وحفظ الحملات ونتائج الإقفال من الواجهة.

فتح نموذج تعديل أو تنزيل PDF موجود يثبت الوصول/العرض لذلك المثال، ولا يثبت نجاح حفظه أو قواعده أو آثاره على باقي النظام. وبيانات Seeder الجاهزة قد تمر بمسارات مختلفة عن FormRequest والواجهة.

**مطلوب قبل القبول:** دورة جديدة مميزة بمعرفات يمكن تتبعها: جهة → عقار وملاك ومستندات → إسناد → مزاد → طلب إقامة كامل → اعتماد → حملات → إقفال مختلط ثم نهائي حسب القواعد → توليد وتنزيل المخرجات الأربع ومطابقتها بالمدخلات. يليها اختبار محاولات التعديل الممنوعة وأخطاء validation والعضوية والعزل.

## R-06 — أداة مقارنة PDF لا تثبت المطابقة المعلنة

**الأولوية:** عالية بالنسبة لقبول المخرجات. **الثقة:** مثبت من السكربت وملف نتائجه.

- `scratch/compare-pdfs.mjs` يستخرج النص وأبعاد الصفحات وعددها، ثم يفحص وجود كلمات في الناتج. لا ينفذ مقارنة بصرية للصفحات أو قياس فرق الصور، ولا يقارن مواضع الحقول، ولا يطابق كل قيمة مع قاعدة البيانات، ولا يختبر الروابط والقص والتداخل والتوقيعات.
- عند `:174` يسجل مرجع **عسير** `refs.asirRef` لفحص **المخرجات**، رغم أن مرجعها المذكور في التقرير هو الحرم. مرجع الحرم يُستخرج لكنه لا يُستخدم في كائن المقارنة الأخير.
- `scratch/pdf-comparison-summary.json` يسجل كل نتائج `keywordAudit` بقيمة `false` للوثائق الأربع، رغم إعلان المطابقة الكاملة. النص العربي المستخرج يحتوي تشكيل حروف وعرضًا مجزأً؛ فشل البحث النصي لا يثبت وحده غياب العبارة من PDF، لكنه بالتأكيد لا يثبت نجاح الفحص.
- جميع قيم `fileSize` في summary صفر، رغم أن ملفات التنزيل لها أحجام فعلية. القياس يُقرأ من Uint8Array بعد تمريره للمحرك؛ لا ينبغي اعتماد هذه الحقول كدليل حجم صحيح دون إصلاح القياس والتحقق.
- السكربت لا يفشل العملية عندما يفشل keyword audit أو تختلف النتائج؛ إنه يكتب ملخصًا ويطبعه.
- ملفات المزاد 4 تُستخرج أيضًا، لكن كائنات المقارنة الأربعة تستخدم المزاد 12 فقط.
- اختلاف 19/20 صفحة و7/9 صفحات قد ينتج طبيعيًا عن اختلاف البيانات وصفحات المتابعة. لا يثبت الخلل، ولا يثبت التطابق.

**مطلوب قبل القبول:** تحديد المرجع الأصلي المعتمد ومصدره لكل ملف؛ ملفات `output/pdf` أمثلة مولدة وليست بمفردها دليل اعتماد رسمي. ثم مقارنة بصرية للصفحات والقوالب الثابتة مع معالجة الحقول المتغيرة، ومطابقة نصية/رقمية واعية بالعربية، وتحقق من المحتوى والروابط والصفحات الإضافية، ونتيجة قبول قابلة للفشل بدل وصف «100%» غير مقاس.

## R-07 — السجلات الخام تحتوي فشلًا يحتاج تسوية مع النتيجة النهائية

أمثلة موجودة:

- `scratch/stage3-part2-report.json:31`: خطوة تعديل المستأجر `FAIL`، مع توقف لاحق عند نافذة التأكيد.
- `scratch/stage2-continuation-report.json` و`finish-stage2-report.json`: أخطاء timeout.
- `scratch/stage7-report.json` و`stage7-continuation-report.json`: خطأ selector ثم navigation timeout.

توجد سكربتات استكمال ومحاولات تشخيص. لذلك لا أعد كل timeout عيبًا في المنتج، ولا أجزم بأن كل هذه السيناريوهات بقيت فاشلة. لكن تقرير الاعتماد يجب أن يربط كل فشل بإعادة تشغيل محددة ناجحة، ويذكر إن كان السبب في الأتمتة أو المنتج، بدل حذف تاريخ الفشل من الخلاصة.

الادعاء بـ24 اختبارًا و183 assertion نُقل في الرسالة المرفقة. لم أُعد تشغيل هذه المجموعة ولم أتحقق من سجل مستقل محدد يطابق الرقمين أثناء هذه المراجعة. لا أستخدمه لإثبات قبول التعديلات الجديدة.

## R-08 — جرى تنفيذ إصلاحات أثناء الجولة خلاف ترتيب المستخدم

المستخدم طلب تسجيل الأخطاء والعمل عليها بعد انتهاء الجولة. التقرير يقول إن BUG-01 إلى BUG-05 أُصلحت، و`git diff` يؤكد تعديلات تنفيذية في JavaScript وController وحذف الشركات/cPanel وملفات بحث وغيرها.

لم أرجع هذه التغييرات. يجب تمييز نتائج ما قبل الإصلاح وما بعده وربط كل إصلاح باختبار regression. تعديل حساس مثل إسقاط قواعد المستأجرين لا يكفي اعتماده لأن مثال الحذف النهائي اختفى من الجدول.

## ما تأكد وما لم يتأكد في هذه المراجعة

| البند | النتيجة |
| --- | --- |
| وجود تقرير وملفات نتائج وسكربتات وتنزيلات | مؤكد من الملفات |
| خروج المستأجر `etmam_lot_34674` وقاعدته من الحالة الحالية | مؤكد بفحص قراءة فقط |
| خلو PHP المعدل من أخطاء syntax | `php -l` نجح لفئات CompanyService وCpanelService وDashboardNotificationController |
| خلو التغييرات المتتبعة من أخطاء whitespace | `git diff --check` نجح |
| نجاح جولة المتصفح كاملة دون تجاوزات | غير مثبت، وتوجد تجاوزات مثبتة في مرحلة 6 |
| نجاح دورة مزاد جديدة كاملة من UI | غير مثبت بالسكربت/التقرير المقدمين |
| مطابقة PDF بصرية/رقمية 100% | غير مثبتة بأداة المقارنة الحالية |
| سلامة حذف tenant عند فشل DB/ملفات/cPanel | غير مثبتة، مع مشاكل تنفيذية موضحة أعلاه |

## ترتيب الاستكمال

1. تعليق اعتماد «100%» وإعادة تصنيف التقرير إلى تنفيذ جزئي مدعوم بأدلة، مع تحديد الفشل والاستكمال والتجاوزات.
2. استكمال دورتي مستخدم/دور المستأجر ودورة المزاد من الواجهات دون كتابة DB لتجاوز سلوكها.
3. تثبيت الحالات التي تكشف عيوب حذف المستأجر، وتجهيز اختبارات سلامة قبل إصلاحها في الجولة المتفق عليها.
4. مراجعة PDF بالمرجع الصحيح وبمقارنة بيانات وتصميم قابلة للتحقق، مع فصل اكتمال البيانات عن مطابقة القالب.
5. إعادة اختبار المسارات المتأثرة بكل إصلاح بعد الاتفاق على الإصلاحات، وتحديث سجل النتائج بالأدلة الفعلية.
